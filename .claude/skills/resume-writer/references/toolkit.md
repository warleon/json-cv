# Resume content toolkit

Supporting material for `SKILL.md`. Pull from here while drafting — none of this is a template to copy verbatim; adapt wording to the user's real facts.

## The achievement formula

**Action + Technical implementation + Context + Result**

> Designed and implemented 10+ backend microservices using Node.js and TypeScript, automating internal operational workflows and reducing manual intervention for the operations team.

- Action: *Designed and implemented*
- Implementation: *Node.js and TypeScript microservices*
- Context: *internal operational workflows*
- Result: *reduced manual intervention*

Not every bullet needs all four parts — but if a bullet has none of them (just names a task), it's probably describing a responsibility, not an achievement. Rewrite it.

## Strong action verbs by category

| Category | Verbs |
|---|---|
| Architecture | Architected, designed, structured |
| Development | Engineered, developed, implemented |
| Leadership | Led, coordinated, mentored |
| Optimization | Optimized, accelerated, streamlined |
| Problem solving | Resolved, diagnosed, investigated |
| Automation | Automated, orchestrated, integrated |
| Infrastructure | Deployed, configured, provisioned |
| Improvement | Refactored, modernized, enhanced |
| Delivery | Launched, delivered, established |
| Research | Evaluated, investigated, benchmarked |

Avoid weak openers that hide the actual contribution: *responsible for, worked on, helped with, participated in, involved in, assisted with.* Not forbidden outright, but almost always a sign the bullet should be rewritten to say what actually changed.

## Quantification dimensions

Numbers make an accomplishment easier to believe and easier to scan. Think across these dimensions when asking the user for a metric, or when deciding which number to surface:

| Dimension | Possible metrics |
|---|---|
| Scale | Number of users, requests, services |
| Performance | Latency, execution time, throughput |
| Efficiency | Hours saved, reduced manual tasks |
| Quality | Error rates, bugs, uptime |
| Business | Revenue, conversion, acquisition |
| Complexity | Integrations, microservices, workflows |
| Adoption | Active users, teams, customers |
| Delivery | Deployment frequency, delivery time |

If there's no exact measurement, a defensible estimate or scope indicator ("10+ microservices", "a small team of 3") is fine. A number that was never measured and isn't a defensible estimate is not fine — ask instead of inventing it.

## Weak vs. strong summary

**Weak:** "I am a passionate software developer with experience in many programming languages and technologies. I am a hardworking person who enjoys learning new things and working in teams."

**Strong:** "Full Stack Software Engineer with 4+ years of experience building production applications and backend systems using TypeScript, Node.js, React, and cloud technologies. Experienced in designing scalable services, automating operational workflows, and delivering solutions that improve business efficiency."

The strong version leads with professional title, gives a concrete experience window, names real specialties, and ties them to business value — no personality adjectives doing the work instead.

## Keyword tailoring in context, not in a list

Given a posting asking for Node.js, TypeScript, REST APIs, PostgreSQL, microservices, AWS, Docker — don't just pile these into the skills section. Weave them into a highlight so they show the technology *in use*:

> "Designed and implemented TypeScript-based Node.js microservices, exposing REST APIs and integrating PostgreSQL databases. Containerized backend services using Docker and deployed applications to AWS."

Only do this for technologies the user has actually used — matching the posting's exact terminology is only valuable when it's also true.

## Project description: show the engineering, not the tech list

**Weak:** "Built a mobile app using React Native and Firebase."

**Strong:** "Designed and implemented an offline-first application for agricultural field data collection, featuring local SQLite persistence, synchronization with a centralized database, and dynamically configurable forms for phytosanitary inspections."

The strong version demonstrates offline-first architecture, data synchronization, and database design through what was actually built — not by naming the stack and stopping there.
